# Mod smoke harness

Starts one Minecraft/loader/Bridge target through the launcher's production startup path without a Tauri window. This developer tool installs game files into its data directory, opens a real game window and terminates only its own spawned process.

## Usage

Install Rust stable/Cargo and the OS-native desktop build prerequisites in
[CONTRIBUTING](../../CONTRIBUTING.md#development-setup), even though this harness opens no
Tauri window. Prepare the JDKs and distribution with the [mod build instructions](../../mod/README.md#build-and-development).
The wrappers run Cargo's `smoke_cell` test with the `smoke` feature; they do not use a prebuilt launcher.

The input distribution is `mod/build/mod-index/`, generated by `modIndex`, or a directory selected with `PUMPKIN_SMOKE_DIST`. Use a data directory outside the repository with space for versions, libraries, assets, runtimes and instances. `CARGO_TARGET_DIR` can keep Cargo output in a separate directory; the wrapper compiles the smoke-enabled launcher test.

Run from the repository root:

```sh
PUMPKIN_SMOKE_DATA=/path/to/data tools/mod-smoke/run.sh 26.3-fabric release
```

```powershell
.\tools\mod-smoke\run.ps1 -Cell 26.3-fabric -Data D:\pumpkin-build\smoke\data -Scenario release
```

## Configuration

| Variable | Purpose | Default |
|---|---|---|
| `PUMPKIN_SMOKE_CELL` | Node id from `mod/nodes.txt` | Unset: test skips |
| `PUMPKIN_SMOKE_DATA` | Launcher data directory | Wrapper's temporary `pumpkin-smoke` directory |
| `PUMPKIN_SMOKE_DIST` | Index and JAR directory | `mod/build/mod-index` |
| `PUMPKIN_SMOKE_OUT` | Reports and logs | `<Data>/smoke-reports` |
| `PUMPKIN_SMOKE_SCENARIO` | Scenario below | `hold` |
| `PUMPKIN_SMOKE_TIMEOUT_SECS` | Startup time limit | `240` |
| `PUMPKIN_SMOKE_LOADER_VERSION` | Exact loader version | Latest stable |

PowerShell exposes the corresponding `-Cell`, `-Data`, `-Dist`, `-Out`, `-Scenario`, `-TimeoutSecs` and `-LoaderVersion` parameters.

| Scenario | Behavior |
|---|---|
| `hold` | Keeps the JAR's `FILE_SHARE_READ` handle open until the run ends |
| `release` | Releases the handle after game startup, as the launcher does |
| `wrong-jar:<node>` | Supplies another node's JAR to exercise startup failure handling |
| `spawn-java:<path>` | Starts the game with a different Java executable from the admission gate |
| `duplicate-id` | Adds a duplicate mod id in the instance to exercise injection refusal |

## Output and limits

Each completed run writes `<cell>__<scenario>.json` and `.game.log`; launcher tracing writes
the corresponding `.launcher.log`. Reports describe the verdict, strategy, startup evidence,
injected arguments and duration. A setup failure can leave a launcher log without a JSON report.

Representative **field values**, not a recorded run (reports contain additional fields):

```json
{
  "cell": "26.3-fabric",
  "scenario": "release",
  "result": "passed",
  "proof": "bridge-ready [\"home\", \"friends\"]",
  "breaker": null
}
```

The serialized verdict field is **`result`** (`passed`, `failed` or `timeout`).
For `hold`/`release`, `proof` requires an accepted, owner-checked Bridge connection and
`ready` advertising both `home` and `friends`, retained through the UI hold; it is not
proof that a person saw the rendered menus. `reason` explains the verdict, `evidence`
contains selected log lines, and `injectedJvmArgs`, `injectedGameArgs`, `javaMajor`,
`loaderVersion`, `seconds` and `exitCode` describe the actual startup.

Contrast a representative `duplicate-id` refusal:

```json
{
  "scenario": "duplicate-id",
  "result": "passed",
  "reason": "the gate refused to inject beside the copy in mods",
  "proof": null,
  "breaker": null
}
```

Here `passed` means the gate correctly refused injection, **not** that Bridge started.
For expected-failure scenarios such as `wrong-jar:<node>`, a recognised startup failure
can pass with a populated `breaker` instead. Interpret `scenario`, `reason`, `proof`
and `breaker` together. The schema and verdict rules are
[`report.rs`](../../src-tauri/tests/smoke/report.rs),
[`observe.rs`](../../src-tauri/tests/smoke/observe.rs) and
[`main.rs`](../../src-tauri/tests/smoke/main.rs).

The harness **does not update `mod/verified.json` or the input distribution**. Its
`DistSource` marks nodes verified only in the in-memory test index so unrecorded cells can
exercise the production gate. Packaging reads the separate repository evidence record;
a passing report does not automatically make a cell available in a release. A negative
scenario may pass because the expected refusal/breaker occurred, not because the JAR started.

Startup evidence does not establish authenticated invitations, world sharing or cross-network joining. Negative scenarios exercise the startup breaker rather than proving normal play. See the [mod build reference](../../mod/README.md) for target definitions and [Bridge contract](../../docs/bridge/README.md) for the channel.

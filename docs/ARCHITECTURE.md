# Architektur

Desktop-App auf Basis von **Tauri 2**: ein Rust-Backend (`src-tauri/`) und ein React-Frontend (`src/`), verbunden über Tauri-Commands (`invoke`).

```
┌──────────────── Frontend (WebView) ────────────────┐
│ React Router → Seiten (Start, Bibliothek, Instanz,  │
│          Entdecken, Skins, Einstellungen)           │
│ TanStack Query ─► lib/api.ts ─► invoke(...)         │
│ Zustand: UI- und Launcher-Einstellungen (persist)   │
└───────────────────────┬────────────────────────────┘
                        │ Tauri IPC (JSON, camelCase)
┌───────────────────────▼──── Backend (Rust) ────────┐
│ commands.rs   dünne Tauri-Commands, Eingabeprüfung  │
│ state.rs      AppState: Stores + Fachlogik (Manager)│
│ services/     store (JSON), auth, download, launch  │
│ models.rs     Instance, ModLoader, Mod, ModSource,  │
│               ModpackOrigin, Template, Account      │
│ error.rs      AppError → { code, message, key… }    │
└────────────────────────────────────────────────────┘
```

## Pumpkin Bridge und Feature-Module

`mod/` ist die clientseitige **Pumpkin Bridge** (`pumpkin_bridge`), nicht eine Friends-Mod mit umbenanntem Button.
`dev.laux.pumpkin.bridge.transport` hält Verbindung, Zustellung und Requests; `modules.friends.FriendsClient`
besitzt Friends-Zustand, Bereinigung und Feature-Operationen. Gemeinsame Layouts/Widgets liegen unter `ui/model`
und `ui/kit`; `ui/home/BridgeHomeScreen` rendert registrierte `BridgeModule`-Kacheln ohne Friends-Fachlogik.
`FriendsScreen` und seine Dialoge liegen unter `modules/friends/ui`.

Fabric hängt denselben freistehenden Logo-Button in Haupt- und Pausemenü ein, ohne Vanilla-Widgets zu verschieben.
Zurück/ESC folgt dem Screen-Elternpfad; der Home-Einstieg hält seinen Friends-Screen für Tab-/Scroll-/Fokus-Erhalt.
Versionsunterschiede bleiben in `compat/` bzw. `platform/`, der Core bleibt Minecraft-frei.

Im Launcher gehört Einspeisung, Index, Materialisierung und Startfehler-Sicherung zu `services/modbridge/ingame/`.
`lib.rs` startet den gemeinsamen Loopback-Listener unabhängig vom Friends-Opt-in. Die vorhandenen globalen/
Instanz-Schalter und Konto-/Loader-Prüfungen bleiben erhalten; Friends-Daten, Netzwerk und Aktionen benötigen
weiterhin die Friends-Freigabe. Ausschalten, Identitätswechsel und Zurücksetzen widerrufen private Topics,
Scopes und alte Arbeits-/Publikationsgenerationen, nicht den Listener. Eine bei Widerruf blockierte private
JSON-Schreiboperation darf ihren einzelnen Socket schließen; der Start-Token bleibt für Reconnect gültig.

Die bestehenden Tauri-Commands/Ereignisse `friends_ingame_*` / `friends-ingame*` bleiben die API der
Instanz-Einstellungen. Sie sind keine Java-Mod-Identität und kein zweiter Einspeisungspfad.
Build-/Versionsmatrix und Bedienung: [mod/README.md](../mod/README.md).


## Backend (`src-tauri/src`)

| Modul | Aufgabe |
|---|---|
| `lib.rs` | Einstieg: tracing initialisieren, Plugins registrieren (siehe „Plugins und Berechtigungen“), AppState laden, Commands registrieren; im Hintergrund dann `worlds::remove_leftovers`, `pack_update::recover_interrupted` und `content::adopt_untracked`. Unter macOS meldet `RunEvent::Opened` geöffnete `.mrpack`-Dateien (siehe `pack_open.rs`) |
| `pack_open.rs` | `.mrpack`-Dateien, mit denen der Launcher geöffnet wird (Dateizuordnung `mrpack` in `tauri.conf.json` unter `bundle.fileAssociations`: Doppelklick, „Öffnen mit“). Beim ersten Start steht die Datei in der Kommandozeile, bei einem zweiten Start liefert sie das `single-instance`-Plugin, unter macOS das Betriebssystem. Nur existierende Dateien mit der Endung `.mrpack` zählen. Das Backend merkt sich die letzte (`OpenedPack`) und sendet das Event `pack-opened`; die Oberfläche holt sie einmalig mit `pack_open_take` und zeigt den Import-Dialog |
| `error.rs` | `AppError` via `thiserror`; serialisiert als `{ code, message }` ans Frontend, umgestellte Meldungen zusätzlich als Fehlercode mit `key`, `params` und `details` (`coded!` in `error/text.rs`: der Code muss im deutschen Wörterbuch `src/i18n/de/errors*.ts` stehen, sonst kompiliert es nicht; Rust zeigt denselben deutschen Text, das Frontend übersetzt ihn in `lib/errors.ts`, rohe Texte fallen unverändert durch). `is_retryable`: Ablehnungen des Servers (4xx außer 408 und 429, dazu `Refused` mit eigener Meldung) versucht kein Download erneut |
| `models.rs` | Datenmodelle, `serde(rename_all = "camelCase")` – Spiegel in `src/lib/types.ts`; dazu die Prüfungen der Eingaben (Namen, `InstanceIcon::validated`, `InstanceScene::validated`, Notizen bis `MAX_NOTES_LEN`) |
| `state.rs` | `AppState`: je ein `JsonStore` für Instanzen, Vorlagen, Konten und Skins, dazu der Laufzeitzustand: laufende Spiele, abbrechbare Vorgänge (`cancellable`/`cancel`) und der `operation`-Lock, der Installation, Inhalts-Vorgänge und Start nacheinander ablaufen lässt und bei laufender Instanz verweigert |
| `commands.rs` | Dünne Commands für Instanzen, Installation, Start und Loader-Versionen: Eingabe prüfen, an `AppState`/Store delegieren, loggen. `update_instance` prüft JVM- und Spielargumente (`services/launch_args`), Notizen, Fenstergröße und einen geänderten Java-Pfad; `instance_launch` sichert zuerst geänderte Welten (`worlds::backup_before_launch`), prüft dann die Standards des Launchers (JVM-Argumente, Fenster) ebenso und holt den Stand eines unterbrochenen Pack-Updates zurück (`pack_update::recover_instance`). Eigene JVM-Argumente und Fenster der Instanz gelten vor denen des Launchers (`launch::effective_jvm_args`, `effective_window`). Nach dem Spielende: Spielzeit, Sitzungsprotokoll sichern (`services/sessionlog`), bei einem Absturz verdächtige Mods aus dem Bericht (`services/crashreport`) |
| `account_commands.rs` | Dünne Commands für Microsoft-Konten und `offline_allowed` |
| `services/store.rs` | Generischer `JsonStore<T>`: in-memory + atomares Schreiben (tmp + rename); `modify(id, …)` ändert einen Eintrag unter dem Store-Lock, so geht keine gleichzeitige Änderung verloren; unlesbare Einträge (neuere Version) bleiben in der Datei erhalten |
| `services/mod.rs` | Modul-Register der Services; re-exportiert die gemeinsamen Helfer (`Dirs`, `blocking`, Dateisystem-Hilfen) |
| `services/dirs.rs` | `Dirs`: Verzeichnislayout (geteilter Cache, Instanz-Verzeichnisse) |
| `services/fsutil.rs` | Dateisystem-Hilfen: Ordner durchlaufen (`walk`), atomar schreiben, ZIPs schreiben (ZIP64 ab 2 GiB), Papierkorb, freie Dateinamen |
| `services/tasks.rs` | `blocking`: Dateiarbeit im Thread-Pool, die beim Abbruch zwischen zwei Dateien aufhört (`check_cancelled`); `lock` für geteilten Zustand |
| `services/progress.rs` | Fortschritt langer Vorgänge: `Phase`, die Rückruf-Typen der Services und das Event `content-progress` |
| `services/transport.rs` | Gemeinsame Bausteine der Downloads: Client-Grundlage ohne automatische Weiterleitungen (`follow_redirects` prüft jedes Ziel), begrenztes Lesen (`read_capped`, `save_capped`) und Prüfsummen (SHA-1/256/512) |
| `services/zip_guard.rs` | Prüfungen für ZIPs aus fremden Quellen: Sonderdateien, ZIP-Bomben (Eintragszahl, Größe, Kompressionsverhältnis) und Pfadkonflikte; die Grenzen gibt der Aufrufer vor |
| `services/limits.rs` | Zentrale Grenzen für Downloads, Archive und Kataloge (Datei-, JSON-, Pack- und Eintragsgrenzen, Parallelität, Seitengröße, Statusantwort eines Servers, Icons); wer sie ändert, ändert eine Sicherheitsgrenze |
| `services/dataurl.rs` | `data:`-URLs (Bilder für die Oberfläche ohne Datei-Freigabe) |
| `services/auth/` | Microsoft-Konto → Xbox Live → XSTS → Minecraft (Refresh-Token im OS-Schlüsselbund). `mod.rs` hält den Ablauf (Konten, Sitzung, Offline-Account), `oauth.rs` die Microsoft-OAuth-Aufrufe (Gerätecode, PKCE-URL, Token-Endpunkt), `xbox.rs` Xbox/XSTS/Minecraft samt Besitz und Profil, `callback_server.rs` den Loopback-Listener, `keyring.rs` den Schlüsselbund. Die Anmeldung läuft standardmäßig im Browser (PKCE, Rücksprung auf `http://localhost:<Port>` an den Loopback-Listener), mit `method = "device"` oder wenn der Listener nicht startet per Gerätecode. Offline-Account (UUID nach `OfflinePlayer:<name>`, MD5/v3) nur, wenn `offline_allowed` (Debug-Build oder angemeldetes Microsoft-Konto, siehe `docs/ACCOUNT-SETUP.md`) |
| `services/mojang.rs` | serde-Formate von piston-meta: Version-Manifest v2, Versions-JSON, Asset-Index |
| `services/rules.rs` | Mojang-`rules` (os/arch/features), Arch-Filter für Natives-Classifier (`natives-macos-arm64`, `natives-windows-x86` …), Classpath-Trenner je OS (`;` unter Windows, sonst `:`) |
| `services/download.rs` | HTTP-Client, SHA-1-geprüfte Downloads mit Retry (nicht bei `AppError::is_retryable` = false), 16 parallel (`buffer_unordered`), gestreamt auf Platte, Fortsetzen per HTTP-Range auf `.part`. Nur vertraute Hosts (`TRUSTED_HOSTS`: Mojang, Loader-Maven, Maven Central) einschließlich jeder Weiterleitung, Größenlimit je Datei (`FILE_LIMIT`) und je JSON-Antwort (`META_JSON_LIMIT`) |
| `services/java.rs` | Mojangs Java-Runtime (`java-runtime/…/all.json`, Komponente aus `javaVersion.component`; Plattform-Schlüssel `windows-x64`, `windows-arm64`, `linux`, `linux-i386`, `mac-os`, `mac-os-arm64`, auf ARM ohne passende Runtime die x64-Runtime in der Emulation; unter Unix Exec-Bit und Symlinks aus dem Manifest); Wahl beim Start: eigener Pfad der Instanz → Einstellung des Launchers → mitgelieferte Runtime, eigene Pfade müssen auf eine vorhandene `javaw.exe`/`java.exe` (Linux/macOS: `java`) zeigen |
| `services/install.rs` | Installation in Schritten, `InstallStep`, `InstallProgress`, Event `install-progress`; Installiert-Marker je Instanz (`mark_installed`, `is_installed`) |
| `services/loader/mod.rs` | Mod-Loader: Loader-Versionen (`versions`), `plan_install` (löst die Loader-Version auf und lädt die Versions-JSON, bei Fabric/Quilt schon mit dem Profil gemerged), `InstallPlan::install` (Vanilla, danach bei Forge/NeoForge der Installer), `installed_version` (Versions-JSON zum Start ohne Netz) |
| `services/loader/fabric.rs` | Fabric- und Quilt-Meta (`meta.fabricmc.net/v2`, `meta.quiltmc.org/v3`, `Flavor`): Loader-Versionen, Launcher-Profil (`inheritsFrom` Vanilla), Merge mit der Vanilla-Versions-JSON |
| `services/loader/forge.rs` | Forge (ab Minecraft 1.17) und NeoForge (ab 1.20.1) über den offiziellen Installer: `check_loader` lehnt ältere Versionen klar ab, Loader-Versionen aus den Maven-Metadaten, Installer mit Prüfsumme aus dem Maven; `install_profile.json` liefert Libraries und Processors, die mit der Java-Runtime das Client-JAR patchen; das Profil (`inheritsFrom` Vanilla) wird wie bei Fabric gemerged. Ein vollständig installiertes Profil wird nicht erneut gebaut |
| `services/loader/maven.rs` | Maven-Repositories der Loader: Koordinaten als Pfade, Artefakt-URLs und ihre `.sha1`-Dateien |
| `services/mods.rs` | Globaler Mod-Cache (`cache/mods/<sha1>.jar`) und Abgleich nach `mods/` der Instanz (Hardlink, Fallback Kopie; bestehende fremde Dateien werden nicht ersetzt); fehlt ein Cache-Eintrag, stellt `recache` ihn für Kopie und Export aus der abgelegten Datei wieder her |
| `services/modrinth.rs` | Modrinth-v2-Katalog, Versions-/Dependency-Auflösung (nur Versionen, die in Loader und Minecraft-Version der Instanz laufen; Quilt nimmt auch Fabric-Mods), Abfragen per SHA-1 und hashgeprüfte Downloads |
| `services/providers/` | Weitere Kataloge in Modrinth-Formen: `ftb.rs` (öffentliche FTB-API, installierbar, Downloads nur von festen Hosts mit Prüfsumme), `technic.rs` (Suche, Details und Installation: Pack-Zip des Autors über `net.rs` = nur HTTPS auf Port 443 und öffentliche Adressen, auch ohne IPv6-Übergangsadressen, die eine IPv4-Adresse einbetten (NAT64, 6to4, Teredo), Loader aus `bin/version.json`), `curseforge/` (CurseForge über den Worker in `proxy/`, der den Schlüssel hält; Suche, Mods mit Abhängigkeiten, Modpacks per `manifest.json` (auch aus einer lokalen `.zip`: `providers::import_curseforge_zip`), Dateien direkt vom CDN; Details unter „CurseForge“). FTB liefert zusätzlich das Änderungsprotokoll einer Pack-Version (`ftb::changelog`). Gemeinsam: `search.rs` (Suchanfrage mit einmal geprüften Grenzen), `source.rs` (`Source`), `remote_file.rs` (Datei eines Packs: Ausweich-Adressen, Wiederholungen, Prüfung gegen Größe und Prüfsummen), `cdn.rs` (Downloads von den FTB-CDNs, nur feste Hosts), `archive.rs` (`zip_files`/`zip_paths`: Pfadregeln und Größengrenzen für Pack-Zips). Pack-Zips werden von der Platte entpackt (`content::Blob::Zip`), nicht im Speicher gehalten |
| `services/mrpack.rs` | `.mrpack`-Export einer Instanz (Vorlagen und „Exportieren…“): Modrinth-Inhalte per SHA-1-Sammelabfrage als Download im Index, alles andere unter `overrides/`, dazu `pumpkin.json` (`requiredBy`, Icon und Szene der Instanz; der Import prüft beide und lässt Ungültiges weg). Der Index trägt Name, Version und optional eine Beschreibung (`PackMeta`, höchstens 64 Zeichen Version und 500 Zeichen Beschreibung; Vorlagen: Name der Instanz, Version „1“) und je verlinkter Datei `env` (`client: required`, `server` nach `server_side` des Modrinth-Projekts, nur wenn es einer der drei Werte des Formats ist). `summary` fragt vorab, wie viele Inhalte verlinkt, eingebettet oder als ausgeschaltet übersprungen werden (`ExportSummary`); `free_targets` wählt für einen Export mehrerer Instanzen in einen Ordner freie Dateinamen („Name (2).mrpack“), so überschreibt er nichts. Vorlagen bleiben unter den Grenzen des eigenen Imports (4000 Dateien, 256 MiB), ein Export hat keine (ZIP64 für große Dateien); abbrechbar, die `.part`-Datei wird entfernt |
| `services/duplicate.rs` | Instanz duplizieren: neuer Eintrag (neue ID, „<Name> (Kopie)“, `lastPlayedAt` leer, Spielzeit 0), Kopie von Spielordner, Natives, Installiert-Marker und Dateiliste des Packs (`pack-files.json`, so lässt sich die Kopie weiter aktualisieren) ohne `logs/`, `crash-reports/`, `.fabric/`; verwaltete Inhalte legt `mods::sync` einzeln per Hardlink ab (als Fortschritt sichtbar, der Abgleich prüft jede JAR); bei Fehler oder Abbruch wird die halbe Kopie entfernt |
| `services/imports/` | Instanzen anderer Launcher übernehmen (nur lesend); je ein Modul pro Launcher, Ablauf unter „Import aus anderen Launchern“ |
| `services/content/` | Sichere Modinstallation und `.mrpack`-Import in neue Instanzen (Ziele exklusiv neu angelegt, kein Symlink unterhalb des Datenordners; darüber, etwa `/var` unter macOS, zählt keiner). `fs_safety.rs`: Pfad- und Dateisicherheit (`write_new`, Zurückrollen); `install.rs`: Modrinth-Inhalt samt Pflicht-Abhängigkeiten; `pack.rs`: `plan_pack`/`import_plan` für Packs von Anbietern und der `.mrpack`-Import; `update.rs`: Update-Suche und Aktualisieren per SHA-1-Abfrage (Mods, Ressourcenpakete, Shader), festgehaltene Einträge (`pinned`) überspringt die Suche; `switch_version` setzt einen Eintrag auf eine gewählte Version (auch eine ältere); `analysis.rs` mit `jar_meta.rs` und `version_range.rs`: Größe und Datum der Dateien und Hinweise aus den Mod-Metadaten (`fabric.mod.json`, `quilt.mod.json`, `META-INF/mods.toml`, `META-INF/neoforge.mods.toml`, eingebettete JARs eine Ebene tief; Lesen mit den Grenzen von `zip_guard`): fehlende Pflicht-Abhängigkeit, doppelte Mod, falscher Loader, falsche Minecraft-Version, bei unbekannter Schreibweise keine Warnung; `adopt.rs`: `adopt_untracked` und `identify` (Erkennung per SHA-1-Sammelabfrage) |
| `services/templates.rs` | Vorlagen: Schnappschuss einer Instanz als `templates/<id>.mrpack` (über `mrpack`, Inhalt: `mods`, `resourcepacks`, `shaderpacks`, `config`, `options.txt`; Welten, Logs und Screenshots bleiben draußen) plus Eintrag in `templates.json`; neue Instanzen entstehen über den normalen Pack-Import. `export_file` legt die Vorlage als `.mrpack` an einen gewählten Pfad (Weitergabe), `import_file` nimmt eine `.mrpack`-Datei als Vorlage auf (geprüft wie der Import einer Instanz; Name aus dem Pack, sonst aus dem Dateinamen) |
| `services/local_files.rs` | Eigene Dateien in eine Instanz: Pfade prüfen (absolut, normale Datei, `.jar`/`.zip`, 1 B bis 256 MiB), Art erkennen (`.jar` = Mod; Zip mit `pack.mcmeta` im Wurzelverzeichnis = Ressourcenpaket, mit Ordner `shaders/` = Shader, sonst fragt die Oberfläche), freie Dateinamen (`name (2).jar`; dieselbe, nur nicht erfasste Datei im Ordner wird übernommen), ein Modrinth-Projekt nur einmal pro Instanz, Cache, Erkennung über `content::identify` (dieselbe SHA-1-Sammelabfrage wie Pack-Import und Nachtragen) |
| `services/pack_selection.rs` | Gewählte Ressourcenpakete und Shader: `options.txt` (`resourcePacks`, `incompatibleResourcePacks`; das letzte Paket gewinnt, eigene Pakete als `file/<Dateiname>`) und Iris (`config/iris.properties`: `shaderPack`, `enableShaders`, Werte wie `Properties.store` maskiert). Geändert werden nur diese Zeilen, alle anderen und die Zeilenenden bleiben; Schreiben über `.tmp` + Umbenennen. Schreibende Commands laufen nur, solange die Instanz nicht läuft: das Spiel schriebe die Datei beim Beenden neu |
| `services/presence.rs` | Discord Rich Presence über `discord-rich-presence` (lokale Named Pipe bzw. Unix-Socket zur Discord-App, kein Netz-Host). Gezeigt werden nur Minecraft-Version, Loader und Startzeit, nie Welt, Server oder Instanzname. `instance_launch` meldet den Start, wenn `LaunchOptions.discordPresence` es erlaubt (Standard aus), `on_game_exit` das Ende; laufen mehrere Instanzen, gilt die zuletzt gestartete. Die Gespräche mit Discord laufen auf einem eigenen Thread, ein fehlendes oder hängendes Discord hält weder Start noch Spielende auf. Die Anwendungs-ID steht in `presence.rs` (`APPLICATION_ID`, leer = keine Verbindung) |
| `content_commands.rs` | IPC für Modrinth, Anbieter, Vorlagen, eigene Dateien, Duplizieren, Export und Import sowie korrelierte `content-progress`-Events |
| `services/pack_update/` | Pack-Updates ohne Weltverlust: `source.rs` plant die neue Version (Modrinth-`.mrpack`, Anbieter-Plan über `providers::plan_pack`, neuere `.mrpack`-Datei bei Instanzen aus einer Datei) und den alten Stand (aus `pack_files.rs`, sonst die installierte Version neu geplant; nicht bei Technic, das nur die neueste Version liefert, und nicht bei Dateien). `diff.rs` entscheidet je Datei aus altem Pack, neuem Pack und Spielordner: ersetzt oder entfernt wird nur, was noch genau so daliegt, wie das alte Pack es brachte; vom Spieler Geändertes oder Angelegtes bleibt, Ausgeschaltetes bleibt aus (die neue Fassung kommt nur in den Cache), Entferntes bleibt weg, auch wenn das Pack es unter neuem Dateinamen bringt (Projekt per SHA-1-Erkennung). `saves/` fasst ein Update nie an. Ablauf: planen, Dateien ohne SHA-1 laden, alle Welten sichern (`worlds::backup`), laden (`stage.rs`: Inhalte in den Mod-Cache, anderes in `instances/<id>/pack-update/new/`), dann wechseln die Dateien auf einem eigenen Thread (`blocking`) in einer Transaktion (`transaction.rs`: Ersetztes und Entferntes liegt bis zum Abschluss unter `pack-update/old/<Pfad>`, neu angelegte Pfade stehen vorher im Journal `pack-update/placed`, die Ziel-Herkunft steht vorher in `pack-update/target`), die bei jedem Fehler, auch beim Speichern von Dateiliste und Instanz, zurückgenommen wird; `recover` stellt nach einem Absturz oder halben Zurücknehmen den alten Stand her (Journal-Pfade entfernen, `old/` zurücklegen; trägt die gespeicherte Instanz schon die Ziel-Herkunft, nur aufräumen) und läuft beim Start, vor jedem Spielstart der Instanz und vor jedem Pack-Update. Festgehaltene Inhalte (`pinned`) lässt `diff::respect_pinned` auf ihrer Version. `mod_list.rs` führt die Inhaltsliste nach; was das Update bringt, gilt als `packManaged`. Fehlen bei CurseForge Dateien, die nur über die Webseite gehen, lehnt das Update ab |
| `services/migrate.rs` | Minecraft-Version und Loader wechseln: nur eine neue Loader-Version lässt die Inhalte unverändert; sonst hebt `version_files/update` (Release, neue Minecraft-Version, Loader des Ziels) die Modrinth-Inhalte, Mods ohne Treffer und nicht prüfbare Mods werden ausgeschaltet, fehlende Pflicht-Abhängigkeiten (höchstens 32) kommen dazu, Mods ohne erfüllbare Abhängigkeit gehen aus. Pack-Instanzen und ältere Minecraft-Versionen mit Welten nur als Kopie (`duplicate_and_migrate`, die Kopie verliert die Pack-Bindung); sonst vorher alle Welten sichern, laden, dann `mods::sync_commit` mit dem Speichern der Instanz |
| `pack_commands.rs` | Dünne Commands für Pack-Updates und den Wechsel von Version und Loader |
| `support_commands.rs` | Fehlerberichte: Log teilen, Debug-Info, gesicherte Protokolle früherer Sitzungen (`log_sessions`, `log_session_read`) |
| `storage_commands.rs` | Dünne Commands für Speicher und Java des Rechners: Übersicht (`storage_overview`), „Cache leeren“ (`storage_clear_cache`, unter der Vorgangssperre), Datenordner im Dateimanager öffnen (`storage_open_dir`) und `java_detect` |
| `services/worlds/` | Welten unter `saves/<Ordner>` (Ordnername = ID): Name, zuletzt gespielt, Spielmodus, Hardcore und Version aus `level.dat` (gzip-NBT über `fastnbt` + `flate2`; unlesbar → Ordnername), Größe, `icon.png` als `data:`-URL (bis 256 KiB). Sicherungen, Wiederherstellen und Löschen liegen in `backup.rs`, `remove_leftovers` in `leftovers.rs`. Sicherung als ZIP `instances/<id>/backups/<Welt>-<Unix-ms>.zip` (Ordner als oberster Eintrag, ohne `session.lock`, über `.part`); Wiederherstellen immer in einen freien Ordner („<Welt> (2)“ …), entpackt mit den Pfadprüfungen von `providers::zip_paths` (ohne die Größengrenzen der Pack-Importe, damit große Welten zurückkommen); Löschen sichert vorher und verschiebt den Ordner erst aus `saves/` (als `backups/<Welt>-<Unix-ms>.deleting`), bevor er entfernt wird. Beim Start entfernt `remove_leftovers` unter `backups/` nur, was ein unterbrochener Vorgang unter genau diesen Namen liegen ließ (`.zip.part`, `.deleting`). Die Sicherungen gehören zur Instanz und werden mit ihr gelöscht; `world_backups_export` (`transfer.rs`) kopiert sie vorher in einen neuen Ordner. `auto.rs` sichert vor dem Spielstart (`instance_launch`) jede Welt, die sich seit ihrer letzten Sicherung geändert hat (jüngste Dateiänderung ohne `session.lock` gegen die jüngste Sicherung); gilt die Einstellung der Instanz (`backupWorlds`) bzw. des Launchers (`LaunchOptions.backupWorlds`), bleiben je Welt die neuesten `backupKeep` (1 bis 50) automatischen Sicherungen, erkennbar am ZIP-Kommentar `pumpkin:automatic`; eigene Sicherungen und die vor dem Löschen bleiben immer. Ein Fehler dabei hält den Start nicht auf. `transfer.rs` importiert außerdem eine Welt aus einem Zip (`world_import`): `level.dat` ganz oben oder in genau einem Ordner, Prüfung der Einträge mit `providers::zip_files` (Pfadregeln, Sonderdateien, ZIP-Bomben), exklusiv in einen freien Ordner („<Name> (2)“), jede Datei genau so lang, wie das Archiv angibt |
| `services/servers.rs` | Serverliste `servers.dat` (NBT ohne Kompression): Name, Adresse, Icon, `acceptTextures`; ändert nur diese Felder, unbekannte Tags und versteckte Einträge (`hidden`, legt das Spiel für Quick Play an) bleiben; Schreiben über `.tmp` + Umbenennen. Einträge werden über ihre Stelle in der sichtbaren Liste angesprochen; Adressen müssen `host[:port]` sein (Hostname, IPv4 oder `[IPv6]`, Port 1 bis 65535; `parse_address`, dieselben Regeln prüft `lib/serverAddress.ts` im Frontend) |
| `services/server_ping.rs` | Server-List-Ping (Handshake und Statusanfrage des Spiels per TCP) für die Statusanzeige der Serverliste: Verbinden und Antwort zusammen höchstens 5 s, Antwort höchstens `SERVER_STATUS_LIMIT` (256 KiB). Gelesen werden nur MOTD (Klartext ohne `§`-Formatierung, höchstens 200 Zeichen, Bausteine bis Tiefe 8), Spieler online/max, Versionsname (höchstens 64 Zeichen) und Antwortzeit; nichts daraus wird ausgeführt oder nachgeladen. Ohne verwendbaren Eintrag, bei Fehler (auch NXDOMAIN) oder Zeitablauf gilt `host:25565`, das Ziel `.` zählt als kein Eintrag. Aus der Antwort werden nur Zielname und Port übernommen |
| `services/datapacks.rs` | Datenpakete einer Welt unter `saves/<Welt>/datapacks/` (`.zip` oder Ordner): Name, Beschreibung aus `pack.mcmeta` (Text-Komponente als schlichter Text ohne `§`-Codes, höchstens 64 KiB gelesen), Zustand nur lesend aus `level.dat` (`Data.DataPacks.Enabled`/`Disabled`, Einträge `file/<Name>`; `level.dat` schreibt allein das Spiel). ### Plugins und Berechtigungen

| Plugin | Zweck |
|---|---|
| `single-instance` | Als **erstes** registriert: ein zweiter Start holt das vorhandene Hauptfenster nach vorn (`unminimize`, `show`, `set_focus`) und beendet sich, statt dieselben JSON-Stores zu schreiben. Steht eine `.mrpack`-Datei in seinen Argumenten, reicht er sie an die laufende Instanz weiter (`pack_open::announce_args`) |
| `opener`, `dialog` | Links/Dateien öffnen, Dateiauswahl |
| `updater` | Neue Version von GitHub Releases (`latest.json`), Signatur gegen `plugins.updater.pubkey` in `tauri.conf.json` geprüft; Ablauf in `docs/RELEASING.md` |
| `process` | Neustart nach dem Update (`relaunch`) |

`capabilities/default.json` gibt dem Hauptfenster nur, was das Frontend braucht: `core:default`, die Fensteraktionen Minimieren, Wiederherstellen (`unminimize`, `set-focus`), Maximieren, Schließen, Ziehen, Icon und Titel (eigene Fensterleiste; Minimieren, Wiederherstellen und Schließen auch für „Beim Spielstart“ in den Einstellungen), `opener:default` („Im Ordner zeigen“) und `opener:allow-open-path` nur für den Spielordner `$APPDATA/instances/*/minecraft` selbst, `crash-reports/*.txt`, `logs/latest.log`, `saves/*` (ein Welt-Ordner) und `screenshots/*.png` (je `*` genau ein Pfadteil), `dialog:default`, `updater:allow-check`/`allow-download`/`allow-install` (suchen, laden, installieren; ohne `download-and-install`) und `process:allow-restart` (kein `exit`). Das rahmenlose Fenster (`decorations: false`) lässt sich nicht per Tastatur verschieben oder in der Größe ändern.

Dateizuordnung: `bundle.fileAssociations` in `tauri.conf.json` trägt `.mrpack` (Rolle Editor); das Öffnen läuft über `pack_open.rs` (siehe Modultabelle). Die Zuordnung (Doppelklick, zweiter Start, macOS-Ereignis) ist noch nicht in einer echten App geprüft.

**Content Security Policy** (`app.security.csp` in `tauri.conf.json`; für den Dev-Server (`devUrl`) injiziert Tauri keine): `default-src 'self'`, `script-src 'self'` (kein Inline-Skript), `style-src 'self' 'unsafe-inline'`, `connect-src ipc: http://ipc.localhost` (die WebView spricht nur mit dem Backend; alle Netzabfragen laufen darüber), `font-src 'self' data:`, `img-src 'self' data: blob: https: asset: http://asset.localhost`, dazu `object-src 'none'`, `frame-src 'none'`, `base-uri 'self'` und `form-action 'none'`. Bilder dürfen per `https:` von überall kommen (Projekt-Icons, Galerien); Beschreibungen aus Katalogen laden Bilder aber nur von vertrauten Hosts (`lib/image-hosts.ts`, `components/Description.tsx`: sonst ein Platzhalter, erst der Klick lädt, weil der fremde Host die IP-Adresse des Spielers sähe). `dangerousDisableAssetCspModification: ["style-src"]` hält `unsafe-inline` für Stile wirksam (Tauri setzte sonst Nonces ein, die es aushebeln). Die CSP ist noch nicht in einem echten Tauri-Build mit Installer geprüft (Schriften, `data:`-Bilder, Asset-Protokoll).

Asset-Protokoll (`app.security.assetProtocol` in `tauri.conf.json`, Cargo-Feature `protocol-asset`): nur für die Vorschau der Screenshots, Scope `$APPDATA/instances/*/minecraft/screenshots/*` (`*` trifft genau einen Pfadteil: eine Instanz bzw. eine Datei direkt im Screenshot-Ordner). Das Frontend macht aus dem Pfad mit `convertFileSrc` eine URL, die WebView lädt die PNG direkt von der Platte; ohne IPC, Base64 oder Verkleinern im Backend. Andere Dateien des Datenordners (Konten, Logs) bleiben darüber unerreichbar; die CSP erlaubt dafür `img-src asset: http://asset.localhost`.

### Persistenz

JSON-Dateien im App-Datenverzeichnis (`app.path().app_data_dir()`; Windows `%APPDATA%\dev.laux.launcher\`, Linux `~/.local/share/dev.laux.launcher/`, macOS `~/Library/Application Support/dev.laux.launcher/`):

- `instances.json`
- `templates.json`
- `accounts.json` (nur `id`, `username`, `kind`, `clientId`; Refresh-Tokens im OS-Schlüsselbund, Dienst `dev.laux.launcher`: Windows-Anmeldeinformationsverwaltung, macOS-Schlüsselbund, unter Linux Secret Service wie GNOME Keyring oder KWallet)
- `skins.json` (Skin-Bibliothek; die PNG-Dateien liegen unter `skins/<sha1>.png`)

Je Instanz liegen außerhalb des Spielordners `instances/<id>/pack-files.json` (was das Pack abgelegt hat, siehe `Instance.modpack`), `session-logs/<Start-ms>.log` (gesicherte Protokolle früherer Sitzungen, damit Exporte und Kopien sie nicht mitnehmen), `backups/` (Weltsicherungen) und während eines Pack-Updates `pack-update/` (Zwischenstand und Journal, siehe `services/pack_update/`).

Der Store liest jeden Eintrag einzeln: Einträge, die dieser Build nicht versteht (etwa eine neue Pack-Herkunft aus einer neueren Version nach einem Downgrade), bleiben für Aufrufer unsichtbar, werden aber bei jedem Speichern unverändert an ihrer Position mitgeschrieben (Warnung im Protokoll nur mit Position und ID); ein neuer Eintrag mit ihrer ID wird abgelehnt (`errors.store.newerEntry`). Unbekannte Felder in lesbaren Einträgen gehen beim Zurückschreiben dagegen verloren. Ist die Datei keine JSON-Liste, wird sie beim Start nach `<name>.corrupt` verschoben (weitere als `<name> (2).corrupt` usw., nie überschrieben), der Store startet leer. Schlägt das Schreiben fehl, wird die In-Memory-Änderung zurückgerollt.

### Datenmodell

- **`ModLoader`**: `vanilla | fabric | quilt | forge | neoforge` – Vanilla ist ein normaler Loader-Wert.
- **`Mod`**: `id`, `name`, `version`, `fileName`, `sha1?`, `enabled`, `source`, `kind` (`mod | resourcepack | shader`, bestimmt den Ordner im Spielverzeichnis), `requiredBy` (siehe „Mods“), `pinned` (festgehalten: die Update-Suche überspringt den Eintrag), `packManaged` (kam mit einem Modpack oder einer Vorlage, gesetzt beim Import).
- **`ModSource`** (getaggt über `type`): `{type:"local"}` · `{type:"url", url}` · `{type:"modrinth", projectId, versionId}` · `{type:"curseforge", projectId, fileId}`.
- **`Instance.modpack`** (`ModpackOrigin?`, getaggt über `type`): merkt sich, aus welchem Modrinth-, CurseForge- oder Anbieter-Pack (`provider`, z. B. FTB; Projekt + Version/Datei) die Instanz stammt, bei einer selbst gewählten `.mrpack` `{type:"file", name, version}` aus ihrem `modrinth.index.json` – Grundlage für Pack-Updates. Was das Pack abgelegt hat, steht in `instances/<id>/pack-files.json` (Pfad → SHA-1, beim Import und nach jedem Update geschrieben).
- **`Template`** (`templates.json`): `id`, `name`, `minecraftVersion`, `loader`, `modCount`, `createdAt`; der Inhalt liegt als `templates/<id>.mrpack` daneben, ohne Verbindung zur Instanz.
- **`LogKind`** (`log_share`): `latest` = `logs/latest.log` des letzten Starts · `crashReport` = neuester Bericht in `crash-reports/`.
- **Startoptionen der Instanz**: `javaPath?` (eigene `javaw.exe` bzw. `java`, sonst Einstellung des Launchers bzw. mitgelieferte Runtime), `window` (`{type:"default"}` · `{type:"size", width, height}` · `{type:"fullscreen"}`), `gameArgs` (nach den Argumenten der Version), dazu `memoryMb?`, `minMemoryMb?` (`-Xms`, ohne Wert gilt der des Launchers, sonst entscheidet die JVM) und `jvmArgs`. `update_instance` prüft einen geänderten Java-Pfad, lehnt Fenstergrößen von 0 ab und prüft JVM- und Spielargumente (`services/launch_args`). Leere eigene Werte der Instanz (RAM, JVM-Argumente, Fenster `default`) lassen die Standards des Launchers gelten.
- **`Instance.playtimeSecs`**: Summe aller Sitzungen; das Backend rechnet sie beim Spielende an (unplausible Dauern über 7 Tage oder bei zurückgestellter Uhr zählen nicht). `update_instance` übernimmt sie wie `lastPlayedAt` (setzt der Start) nie vom Frontend; Inhalts-Vorgänge schreiben nur die Liste `mods`.
- **`Instance.importedFrom?`**: Instanzordner im anderen Launcher, aus dem importiert wurde; `import_detect` markiert solche Quellen als `imported`.
- **`Instance.notes`**: eigene Notizen (höchstens 10 000 Zeichen, `update_instance` prüft das).
- **`ForeignInstance`** (nur Antwort von `import_detect`): `launcher` (`prism | modrinth | curseforge | atlauncher`), `root` (Ordner, unter dem die Suche sie fand), `path`, `gameDir`, `imported`, `unsupported?` (Grund, warum Pumpkin Launcher sie nicht starten kann), `contents` (`sizeBytes`, `mods`, `worlds` des kopierten Spielordners), `name`, `minecraftVersion`, `loader`, `loaderVersion?`, `memoryMb?`, `jvmArgs`, `javaPath?`, `window`, `group?`, `notes`, `icon?` (`data:`-URL) und `notAdopted` (`preLaunchCommand | postExitCommand | wrapperCommand | javaPath | jvmArgs`: was Pumpkin Launcher nicht übernimmt, z. B. Befehle aus fremden Dateien).
- **`Instance.icon?` / `Instance.scene?`**: eigenes Icon (`InstanceIcon`, getaggt: `{type:"glyph", glyph, palette}` mit Namen aus Buchstaben, Ziffern, `-`, `_`, oder `{type:"image", src}` als `data:`-URL in PNG, JPEG, WebP oder GIF bis `ICON_DATA_URL_LIMIT`) und Szene (`{biome, seed}`); ohne Wert gilt das Icon des Modpacks bzw. eines aus der ID, die Szene ergibt sich aus der ID. Gesetzt nur über `instance_set_icon` und `instance_set_scene` (`update_instance` lässt beide unberührt).
- **`Instance.backupWorlds?`**: Wahl dieser Instanz für „Welten vor dem Start sichern“; ohne Wert gilt die Einstellung des Launchers. **`Instance.defaultAccount?`**: Konto, mit dem die Instanz startet (Schlüssel, den das Frontend vergibt); ohne Wert gilt das aktive Konto.
- **`Instance.group?`**: Gruppe in der Bibliothek (getrimmt, leer = keine). Es gibt keine eigene Gruppen-Entität: Gruppen sind die Namen, die Instanzen tragen.
- **`LibrarySkin`**: `id` (SHA-1 der PNG), `name`, `variant` (`classic | slim`), `addedAt`. Dieselbe Datei kommt nur einmal in die Bibliothek.
- **`Screenshot`** (nur Antwort, nicht gespeichert): `fileName`, `path` (absolut), `takenAt` (Änderungszeit in ms), `size` (Bytes).
- **`SkinProfile`** (nur Antwort, nicht gespeichert): `skin: { url, variant } | null`, `capes: { id, alias, url, active }[]`.
- **`ExportSummary`** (Antwort von `instance_export_summary`): `linked`, `embedded`, `skippedDisabled`: wie viele Inhalte der Export als Modrinth-Download verlinkt, in die Datei einbettet oder als ausgeschaltet weglässt.
- **`StorageOverview`** (Antwort von `storage_overview`): `dataDir`, `freeMb?`, `instances: { id, bytes }[]`, `modCacheBytes`, `unusedCacheBytes` (was „Cache leeren“ löscht), `sharedBytes` (Libraries, Assets, Versionen, Runtimes). **`JavaInstall`** (`java_detect`): `path`, `version`, `major`, `vendor?`.
- **`LogSession`** (`log_sessions`): `id` (Startzeit in Unix-ms), `startedAt`, `size`. **`ServerStatus`** (`server_ping`): `motd`, `playersOnline`, `playersMax`, `version`, `latencyMs`.
- **`LaunchOptions`** (nur Eingabe von `instance_launch`): `username` (Offline), `accountId?` (Microsoft), `javaPath?` (Einstellung des Launchers; der Pfad der Instanz geht vor), `defaultMemoryMb?`, `defaultMinMemoryMb?`, `defaultJvmArgs` und `defaultWindow?` (Standards des Launchers für Instanzen ohne eigene Werte; JVM-Argumente und Fenster werden wie die der Instanz geprüft), `backupWorlds?` und `backupKeep?` (Launcher-Einstellung „Welten vor dem Start sichern“ und wie viele automatische Sicherungen je Welt bleiben), `discordPresence?` („In Discord anzeigen“), `quickPlay?` (`QuickPlay`; die Welt muss existieren, die Adresse darf nicht wie eine Option aussehen).
- **`QuickPlay`** (getaggt über `type`): `{type:"world", id}` (Ordnername unter `saves/`) · `{type:"server", address}` (`host[:port]`). **`Instance.lastQuickPlay?`** merkt sich das Ziel des letzten Starts per Quick Play (`world_delete` vergisst es, wenn es die gelöschte Welt war).

- Neue Felder tragen `#[serde(default)]`, damit ältere JSON-Dateien weiter laden.

### Mod-Loader

Die Installation (`loader::plan_install`, `InstallPlan::install`) unterscheidet je `ModLoader`: ein Profil vom Meta-Server (Fabric, Quilt) oder den Installer des Loaders (Forge, NeoForge). Ist `loaderVersion` leer, nimmt `instance_install` den neuesten stabilen Loader und **speichert ihn in der Instanz** (die UI sollte die Instanz danach neu laden). `check_loader` lehnt Forge vor 1.17 und NeoForge vor 1.20.1 mit Grund ab, auch beim Import.

**Fabric und Quilt**

- Profil `versions/loader/<mc>/<loader>/profile/json` des jeweiligen Meta-Servers.
- Fehlende SHA-1 im Profil (Loader, Intermediary) kommen aus den `.sha1`-Dateien des Maven-Repos; das ergänzte Profil liegt unter `versions/<fabric|quilt>-loader-<loader>-<mc>/…json` für den Start ohne Netz.
- Merge: Loader-Libraries vor den Vanilla-Libraries (gleiche `group:artifact[:classifier]` → Loader gewinnt), `mainClass` des Profils (bei Fabric `net.fabricmc.loader.impl.launch.knot.KnotClient`), Profil-Argumente werden angehängt. ID, Client-JAR, Assets und Java bleiben die der Vanilla-Version.
**Forge und NeoForge**

- Erst Vanilla-Client und Java, dann `forge::install` (aus `InstallPlan::install`): Installer laden, seine Processors ausführen (sie patchen das Client-JAR), danach das Profil des Installers mergen. Der Fortschritt zählt Libraries und Processors.

**Für alle Loader**

- Schritte `loader` (Profil bzw. Installer) und `mods` (Abgleich `mods/`) kommen zusätzlich als `install-progress`.
- Der Installiert-Marker enthält bei Mod-Loadern MC-Version, Loader und Loader-Version; ein Wechsel gilt als „nicht installiert“.

### Mods

`instances/<id>/minecraft/mods/` ist der Mods-Ordner (Spielverzeichnis, dort suchen die Loader). `mods::sync` legt jede aktivierte Mod mit `sha1` aus `cache/mods/<sha1>.jar` per Hardlink (Fallback Kopie) unter ihrem `fileName` ab und entfernt deaktivierte nur, wenn die Datei dort denselben SHA-1 hat; fremde Dateien bleiben liegen. Fehlt eine verwaltete Mod im Cache, schlägt der Abgleich fehl. Modrinth-Installationen laden die ausgewählte, zu Loader und Minecraft-Version der Instanz passende Version und erforderliche transitive Dependencies, prüfen Dateigröße, SHA-1 und SHA-512 und füllen den Cache. Updates gibt es nur auf Wunsch (`modrinth_check_updates`, `modrinth_update_mods`), nie automatisch (die Oberfläche fragt vor mehreren Updates mit alt und neu und nimmt sie auf Wunsch zurück: die alten Dateien liegen im Cache, `update_instance` mit dem alten Stand legt sie zurück); nur Modrinth-Inhalte haben eine Update-Quelle (CurseForge-, FTB- und Technic-Inhalte werden nicht auf Updates geprüft); festgehaltene Einträge (`pinned`) überspringt die Suche, und `modrinth_switch_version` setzt einen Eintrag auf eine gewählte neuere oder ältere Version; kollidierende Dateien werden nicht stillschweigend ersetzt. Für Inhalte, die mit einem Modpack kamen (`packManaged`), ist ein Pack-Update der vorgesehene Weg.

„Benötigt von“ (`requiredBy`): Vorlagen legen zusätzlich `pumpkin.json` (`{ requiredBy: { <fileName>: [projectId…] } }`) ins `.mrpack`, der Import wertet sie aus; bei fremden Packs wird es aus den Pflicht-Abhängigkeiten der per SHA-1 erkannten Modrinth-Versionen abgeleitet. Eigene Dateien (Ziehen aufs Fenster im Tab „Inhalte“ oder „Datei hinzufügen…“) laufen über `instance_check_files` (Art, Doppelte) und `instance_add_files`: Cache, Eintrag, `mods::sync`. Was Modrinth per SHA-1 kennt, wird mit Projekt und Version eingetragen und bekommt so Updates; ohne Netz bleibt es lokal und lässt sich später über „Mit Modrinth abgleichen“ (`modrinth_identify`) nachholen. Ein abgelegtes `.mrpack` führt zum Import als neue Instanz (`/instances?neu=1&datei=<Pfad>`). Beim Start trägt `content::adopt_untracked` Dateien aus `mods/`, `resourcepacks/`, `shaderpacks/` nach, die nicht in der Instanz stehen (`*.disabled` → deaktiviert; ohne Netz als lokal), und sendet danach `instances-changed`.

### CurseForge

Der Launcher kennt keinen Schlüssel: alle Abfragen gehen an den Worker in `proxy/` (Regeln aus den API-Bedingungen, vor allem: nichts wird zwischengespeichert, und Forks: `proxy/README.md`). Die Dateien kommen direkt vom CDN.

- Abhängigkeiten werden Ebene für Ebene mit Sammelabfragen (`POST /v1/mods`, `/v1/mods/files`) und der Datei-Wahl aus `latestFilesIndexes` aufgelöst, damit große Bäume unter dem Limit des Workers von 60 Anfragen pro Minute bleiben.
- Auf 429 wartet der Launcher (`Retry-After`, das der Worker mitschickt, höchstens 30 s, sonst 5/10/20 s) und versucht es bis zu dreimal.
- Lehnt das CDN einen Download mit 401 ab, weil CurseForge dafür einen Schlüssel verlangt, nennt die Meldung (`AppError::Refused`) die Datei und den Ausweg (Launcher aktualisieren oder Datei von Hand laden), ohne dieselbe Adresse noch zweimal zu versuchen. 403 bedeutet beim CDN „Datei fehlt“ und bleibt beim allgemeinen Text.
- Nur über die Webseite erlaubte Dateien werden nicht umgangen: das Event `content-blocked` öffnet den Dialog „Von Hand laden“, und `curseforge_adopt_download` übernimmt die Datei aus dem Downloads-Ordner. CurseForge wird erst gefragt, wenn dort eine passend benannte Datei liegt.

### Import aus anderen Launchern

`import_detect` sucht nur lesend unter `PrismLauncher`, `ModrinthApp` und `ATLauncher` im Datenordner des Systems (`dirs::data_dir`, unter Windows `%APPDATA%`), unter `curseforge/minecraft` im Benutzerordner (unter Windows im Ordner „Dokumente“, dem Standard der CurseForge App) oder im gewählten Ordner. Unlesbare Instanzen werden protokolliert und übersprungen, nicht startbare (Forge/NeoForge zu alt) mit Grund in `unsupported` gemeldet.

- `prism.rs` (Prism Launcher/MultiMC): `instance.cfg` mit `name`, `notes`, `iconKey`; RAM (`MaxMemAlloc`, `MinMemAlloc` als `-Xms`), `JvmArgs`, `JavaPath`, Fenstergröße und Befehle nur bei den jeweiligen `Override…`-Schaltern; Befehle (`PreLaunchCommand`, `PostExitCommand`, `WrapperCommand`) werden nie übernommen. Komponenten aus `mmc-pack.json`, Gruppe aus `instgroups.json` neben den Instanzordnern, eigenes Icon aus `icons/<iconKey>.<Endung>`; Spielordner `minecraft`, sonst `.minecraft`.
- `modrinth_app.rs`: SQLite `app.db` per `rusqlite`, schreibgeschützt geöffnet; Tabellen `instances`, `instance_content_sets`, `instance_launch_overrides`, in seit Mitte 2026 nicht mehr geöffneten Datenbanken noch `profiles`. Eine unlesbare Zeile verbirgt nur sich selbst. Spielordner `profiles/<path>` unter `settings.custom_dir` oder dem Datenordner.
- `curseforge.rs` (CurseForge App): `minecraftinstance.json`, Loader aus `baseModLoader.name`, Herkunft der Mods aus `installedAddons[].addonID` und `installedFile.{id,fileName}`.
- `atlauncher.rs`: `instance.json` mit `id` (= Minecraft-Version), `launcher.loaderVersion`, `maximumMemory`, `javaArguments`, `javaPath`, Befehle (nicht übernommen); eigenes Bild `instance.png`; deaktivierte Mods liegen in `disabledmods/`.

Alles aus fremden Dateien läuft durch `Setup::vetted`: JVM-Argumente, die Code laden (`-javaagent`, `-agentpath`, `-XX:OnError`, `@argfile`, Klassenpfad …) oder `services/launch_args` verletzen, kommen nicht mit (`notAdopted: jvmArgs`), ein Java-Pfad nur, wenn `java::custom_java` ihn kennt. Icons liest `read_icon` nur als PNG/JPEG/GIF/WebP bis `limits::ICON_LIMIT`; `update_instance` prüft JVM- und Spielargumente (Anzahl, Länge, keine Steuerzeichen) und die Notizen mit denselben Grenzen.

`instance_import` legt die Instanz an (der gewählte Name, Version, Loader, RAM, JVM-Args, Java-Pfad, Fenster, Gruppe, Notizen, `importedFrom`), kopiert den Spielordner ohne `logs/`, `crash-reports/`, `.fabric/`, `.cache/` und die Dateien des Launchers (`disabledmods/<name>` als `mods/<name>.disabled`), legt die Inhalte in den Mod-Cache (Phasen `copy` und `hash` im Hintergrund-Thread, abbrechbar) und erfasst sie wie `adopt_untracked`: Modrinth-SHA-1-Abfrage, ohne Netz lokal, was die CurseForge App von CurseForge hat, als CurseForge-Inhalt. Bei Fehler oder Abbruch verschwindet der halbe Ordner, auch wenn der Hintergrund-Thread erst danach endet.

### Vorlagen

Eine Vorlage ist der Schnappschuss einer Instanz (`template_save`, im Instanz-Menü „Als Vorlage speichern“) als `.mrpack` unter `templates/<id>.mrpack`: Mods, Ressourcen- und Shaderpakete, `config/` und `options.txt`. Welten, Logs und Screenshots gehören nicht dazu. `template_create_instance` legt daraus über den normalen Pack-Import (`content::import`) eine neue, vom Original unabhängige Instanz an; der Vorgang ist abbrechbar. Das Frontend bietet Vorlagen im Dialog *Neue Instanz* (Reiter „Vorlage“) an und löscht sie dort auch.

### Installation und Mod-Cache

- Installation läuft in benannten Schritten (`InstallStep`: `java → client → libraries → natives → assets → loader → mods`; `loader` kommt bei Fabric/Quilt als Profil-Download vor `java`, bei Forge/NeoForge zusätzlich als Installer-Lauf nach `assets`). Jeder Fortschritt geht als Tauri-Event `install-progress` mit `{ instanceId, step, done, total }` ans Frontend.
- Mod-JARs liegen einmalig in einem globalen, per SHA-1 adressierten Cache (`<app_data>/cache/mods/<sha1>.jar`) und kommen für alle Loader per Hardlink (Fallback Kopie) nach `mods/` (siehe „Mods“).

## Herkunft der Ideen und Lizenz

Architektur und Datenmodell orientieren sich an der Recherche zu NoRiskClient (`docs/research-noriskclient.md`). NoRiskClient steht unter **GPLv3**: übernommen werden nur Ideen und Konzepte, **kein Code**. Protokolle und Formate (Microsoft/Xbox-Auth, piston-meta, Fabric-/Quilt-Meta, Forge-`install_profile.json`, Modrinth, `.mrpack`, CurseForge) werden nach der jeweiligen Primärdokumentation implementiert.

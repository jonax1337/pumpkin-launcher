## Offene Entscheidungen des Entwurfs

- D1: Should 'Spiele aus anderen Launchern erlauben' default to OFF (the spec's choice) or to ON once Friends is enabled? The discovery file lets any mod in any of your games ask for pairing.
- D2: Is it acceptable that turning Friends on for the first time stays launcher-only? Moving it into the game would require a loopback listener even while Friends is off, which breaks the SPEC 12.1 promise that nothing listens before you opt in.
- D3: May foreign games prove their Microsoft account with one call from the game's own vanilla login code to Mojang's session server (no network code of our own in the mod)? Without it, games from other launchers cannot be proven online and cannot host.
- D4: How should Pumpkin Friends sit next to Mojang's own Friends list on 26.2 and later? The spec ships it there, never binds key O, leaves our keybinding unbound by default, and skips the title-screen button when it would overlap Mojang's button.
- D5: When, if ever, should the 'later' cells be scheduled: Forge above 1.20.1, NeoForge 1.20.2-1.20.6, and 1.16.5/1.17.1?

## Review: security (Urteil: fixable)

- **[major]** 6.1 gets the threat baseline wrong, so A8, A9, A13 and 12.1 risk 1 claim a residual risk of 'none' when that is not true. A hostile mod is arbitrary code running as the same OS user. On Windows the identity key lives in Credential Manager (Cargo.toml: keyring with windows-native), which any same-user process can read with CredRead. On Linux, sync-secret-service gives the same access through an unlocked collection. On Windows, a same-user process can also open the launcher with PROCESS_VM_READ and read its memory. So the statement 'cannot read the launcher's memory, the keyring, or the friends identity key' is false on two of three OSes. The same applies to files: mod-audit.json (6.3) and the records holding addedInGame can be edited on disk, so A9's 'cannot hide its traces' does not hold either. The consent and scope design is presented as a security boundary against hostile mods. It is really a guard against misuse of the intended API and against UI confusion.
  - Fix: Rewrite 6.1: code inside the game JVM equals same-user code execution and can take the identity key on Windows and Linux. Restate the purpose of scopes and prompts as limiting abuse through the API by greedy or semi-trusted mods, not as protection against malware. Correct the residuals of A8, A9 and A13 and of risk 12.1/1. Add the keyring exposure to PRIVACY.md (9.6). Keep D1 default OFF and state this reasoning in D1.
- **[major]** The in-game join can be redirected across games (claims of 8.2, A8 and A13). Every game that can read the discovery file holds the token. The same JVM can write that file (same user, 0700 directory owned by that user). On Windows it can also co-bind the bridge port, because the bridge and LocalListener::bind use plain TcpListener::bind with no SO_EXCLUSIVEADDRUSE, so a same-user socket with SO_REUSEADDR can bind the same address:port. A hostile mod in game A can therefore run a fake launcher. Mutual HMAC succeeds because the fake knows or writes the token. Every later foreign game B attaches to the fake, which then shows B made-up invites, prompts and status. It can also answer invite.joinHere with a 127.x.y.z:port it controls and relay B to any remote server. The mod's 127.0.0.0/8 check (8.2 mod step 1, U2b JoinTarget) gives no assurance that the endpoint is the launcher's verified single-owner listener. A8 'none' and A13 cover only a squatter that does not know the token.
  - Fix: (1) Set SO_EXCLUSIVEADDRUSE on Windows for the bridge listener and for every LocalListener (guest join listener), with a Rust test that a second SO_REUSEADDR bind fails. (2) Have the launcher watch discovery.json (hash/mtime). On any change it did not write, rotate the token, rewrite the file, close the external links that are not yet welcomed, and show a warning. (3) Mod: before attaching, check with ProcessHandle.of(pid).info().command() that the pid in the file is alive and that its executable name matches the launcher binary. Log and refuse otherwise. (4) Add a new row to 6.5: 'hostile mod in game A impersonates the launcher toward other foreign games', residual 'possible for same-user code; mitigated by exclusive bind and tamper detection'. Change the A8 residual from 'none' accordingly.
- **[major]** Offline own launches can get around the online-account rule (4.4 step 4, 8.2, compared with SPEC 12.2 and commands.rs:404). An own launch without a Microsoft account gets no env (mod_bridge_env returns empty when online_account is false). Under MOD2 the mod then falls back to the discovery file. 4.4 step 4 binds any discovery link whose owner PID equals a running own launch's Spawned.pid to an instance link with no pairing and no account proof. That contradicts decision 0 ('Offline/cracked games cannot attach') and A10. Separately, invite.joinHere (8.2 launcher step 1) never checks online_account, which breaks SPEC 12.2 'Joining needs a Microsoft account'. Today that rule is enforced only in instance_launch, which joinHere bypasses.
  - Fix: In 4.4 step 4, a discovery link that resolves to an own launch inherits that launch's online_account. If it is false, reject{account} (or admit read-only with no join and no share). Add to 8.2 launcher step 1: 'the link's game has online_account == true, else msAccountRequired'. Add both cases to the 10.2 modbridge and joining test lists.
- **[major]** A14 claims 'none', yet the v1 path still accepts a leaked env token from any process. 4.4 step 4 adds the owner-PID == Spawned.pid check only for attach (v2). 5.9 keeps the hello path byte-identical, and the current server does no PID check at all (no sockowner use in modbridge/). The launcher still sets PUMPKIN_IPC_PROTOCOL=1, so a process holding a leaked token sends hello instead of attach and gets a v1 instance link: friend list, share/kick/stop, and the v1 first-share prompt now mapped to ModPrompt::Scope{share}.
  - Fix: Run owner_of_connection(peer, local) == Spawned.pid on the v1 hello path too, between reading hello and sending welcome. The wire stays unchanged; a mismatch gives reject{token}. Use the same IO-error rule as the v2 env path. Add the test 'v1 hello with a valid token from another PID → reject' to R2's acceptance list.
- **[major]** The account proof (4.6) is not tied to the attaching process and proves less than the UI says. The serverId comes only from public inputs (launcherId from the file, plus nonceA, which goes to the attacker), and player.name/uuid are self-reported. So any same-user process can pass by calling joinServer with the attacker's own Minecraft account from anywhere, or by relaying the nonce to a mod in another game. The pairing prompt still says 'von Mojang bestätigt', and 4.7 sets online_account = true for the external game. That satisfies SPEC 12.2's hosting precondition even when the attaching JVM itself is an offline/cracked game whose integrated server does not authenticate. A11's control ('needs a valid Minecraft session') is therefore met by any Minecraft account at all.
  - Fix: Change the prompt wording to 'Konto <name> bei Mojang angemeldet (nicht geprüft, dass dieses Spiel es nutzt)'. When the UUID is not one of the launcher's signed-in accounts, show that prominently and untick every scope by default, rather than only adding a warning line. For hosting by external games, also require that the status ping of the verified LAN port answers. Optionally require that the proven UUID is a launcher account before online_account is set to true. Update A11 and D3 to describe what the proof actually guarantees.
- **[major]** The rate limits and anti-spam caps can be reset or turned into a DoS. 6.4 keeps the limits and the prompt caps (1 open, 3 per 10 min) 'per link', but 4.7 says a reconnect resumes the link, and 4.3 never says whether counters survive a reconnect or 'Trennen'. If they reset, A4 ('at most 3 per 10 min') and A6 do not hold. Second, sticky pairing denial is keyed on exe path. Every foreign Java game shares javaw.exe/java, so three denials of a hostile attacher (which can spawn fresh child JVMs, each with a new ProcessKey and a new 3-proof budget) silently reject every legitimate foreign game for 10 min. Third, '1 open pairing prompt globally' plus '2 links between step 5 and welcome' lets one attacher starve legitimate games with reject{busy} for 120 s each. Nothing says the pending-2 cap excludes env-token links, so own launches can be starved too. There is also no global cap on account proofs, so the launcher's has_joined calls can be amplified.
  - Fix: Key every 6.4 counter, the prompt caps and grants on game_id (ProcessKey or instance launch), never on the connection, and test that counters survive reconnect and Trennen. Key the 3-denial suppression on (exe path, proven player UUID) and not on exe path alone. Apply the pending-2 cap and the pairing slot only to external attaches; env and own-launch links bypass them. Add a global limit on account proofs (e.g. 10 per 10 min) and on pairing prompts (e.g. 5 per 10 min), and say these limits in 6.4.
- **[major]** The Linux reverse lookup (9.1 sockowner and 4.4 step 1) does not define how it handles unreadable PIDs, which leads to fail-open on one path and DoS on the other. owner_of_connection scans /proc/<pid>/fd for every same-uid PID. Same-uid non-dumpable processes (ssh-agent, gpg-agent, gnome-keyring, browser sandboxes) return EACCES. If that counts as a lookup error, the IO-error fallback ('admit anyway', 4.4 step 4) opens env-token links and A14 is lost, while every discovery link gets notGame. An attacker can also force the error. 4.4 step 6 (re-check before host.invite and joinHere) does not say what happens on an IO error. The existing ProcTable aborts on the first read_dir error.
  - Fix: Specify: EACCES/ENOENT on one PID's fd directory skips that PID. Only a failure to read /proc/net/tcp{,6} or /proc itself is Err. Zero owners is Ok(None), giving notGame. Owner-PID checks for env links and the step-6 re-check fail closed. The admit-on-IO-error fallback is limited to platforms without an implementation (cfg not windows/linux/macos), not to runtime errors. Add a test with a fake process table that contains an unreadable PID.
- **[major]** The launcher's confirmation dialogs can be clickjacked and the window's focus stolen (6.2, 9.3, 9.5). Pairing and danger prompts, and launcher.open (1 per 10 s), restore and focus the launcher window on the mod's request. A hostile mod can open the window under the player's cursor or keyboard at a moment it picks, for example by asking the player in-game to click a spot or to press Tab and Enter. The click or keystroke then lands on 'Ausführen' (identity reset/disable) or 'Erlauben'. Initial focus on 'Ablehnen' does not stop clicks or Tab+Enter.
  - Fix: In ModPromptDialog, keep every non-deny button disabled for at least 1000 ms after the dialog is visible and the window has focus, restarting the delay on each focus or visibility change. Ignore any pointer-up whose pointer-down happened before the dialog appeared. Never restore or focus the window on launcher.open while a prompt is open. Add these rules to the F2a acceptance list and the check script.
- **[major]** The 2.1 floor of 1.18 (3.8, R6, 12.2) brings in Log4Shell-era versions and depends on self-reported versions. MC 1.18 shipped log4j 2.14.1 and relies on launcher-supplied mitigations (Mojang's patched logging config or formatMsgNoLookups). Foreign launchers and old external installs give no such guarantee, and peer chat flows through the tunnel into the host's log and the guest's log. For external links the floor is checked against the self-reported gameReport.minecraft (4.5, A15), so a 1.17 or 1.18.0 game claiming '1.21.1' passes. The floor is also turning into a security rule while being enforced only cosmetically. In addition, the validator choosing the Login Start layout from the guest's protocol VarInt (3.8 step 1) lets the attacker pick the parsing branch.
  - Fix: Set the floor to 1.18.2 (MIN_MC_LABEL '1.18.2'), never 1.18/1.18.1. For external hosting, read version.protocol from the 6.1 status ping (extend ServerStatus), map it to a release, and require it to be at least the floor and equal to the reported version, else versionUnsupported. In mcproto, choose the Login Start layout from the host session's verified version and reject a protocol VarInt that does not match the host.
- **[minor]** Two operations that change trust are classed as 'exposure-reducing (implicit)' (6.2, 5.7). friend.rename changes the alias the user relies on to recognise a friend in invites, guest lists and prompts. Together with A1/A2, a hostile mod can befriend an attacker and rename it to a trusted name like 'Papa', or swap the aliases of real friends, with no prompt and no audit. friend.acknowledge also clears the identityChanged notice, the only signal that a friend's key rotated (SPEC 4.x identityRotated), so a hostile mod can quietly suppress a security warning.
  - Fix: Move friend.rename to the friends scope, add it to the audit and to the undo table (restore the previous alias). Make friend.acknowledge for identityChanged launcher-only, as with addedInGame. Allow only 'renamed' to be acknowledged in-game.
- **[minor]** Self-reported and OS-derived strings can be used to phish (4.5, 6.2 scope prompt, 9.5, 4.5 InstanceSummary.name). The scope and danger prompts open with the game label ('ATM10 (Prism) möchte …'), which comes from the self-reported instanceLabel and brand. A hostile mod can report 'Pumpkin Launcher' or 'Sicherheitsprüfung'. The same label becomes the invite title shown to friends. brand is never listed as sanitised, and exe_path, which an attacker can choose by naming its binary, is shown without 12.3 sanitisation, so bidi overrides such as U+202E are possible.
  - Fix: Run every gameReport string (instanceLabel, brand, fileName) and the exe path through the 12.3 sanitiser, and cap brand at 32. In all prompts, render self-reported fields in a separate 'Selbst angegeben' style. Open the sentence with the verified facts (player UUID-checked name, exe file name, PID). Never put the self-reported label where it reads as the subject of the sentence.
- **[minor]** The discovery path overrides and the connect target are underspecified (4.2). The mod accepts -Dpumpkin.bridge.discovery or PUMPKIN_DISCOVERY_FILE first. Instance JVM arguments and env vars can come from imported modpacks or instances (Prism instance.cfg), so a UNC path such as \\host\share\x.json makes Windows send NTLM credentials and gives that remote file control over the port. The mod has no owner check on Windows, and the spec never says the mod connects only to the literal 127.0.0.1.
  - Fix: Allow the overrides only when the system property pumpkin.dev=true is set (for FakeLauncher), and refuse UNC, network and relative paths. State that the mod always connects to the literal 127.0.0.1 (never 'localhost' and never a host from the file). On Windows, check that the file's owner SID (Files.getOwner) is the current user.
- **[minor]** The handshake size limits contradict each other, and data leaks before authentication (4.3, 4.5, 5.1). manifestPart is sent during the handshake (step 7) under the 16 KiB line cap, yet 150 entries × (128-hex sha512 + up to 128-char fileName + JSON) come to about 45 KiB, so implementers will raise the pre-welcome cap. Also, the unauthenticated attach line (step 1) carries the minecraft, loader and loaderVersion values to whatever listens on the port, which can be another OS user's squatter (A13).
  - Fix: Use 1 KiB per line up to step 5 and 64 KiB from step 5 to welcome, or cap manifestPart at 40 entries. Move mod, minecraft, loader and loaderVersion out of attach into the post-proof gameReport, leaving only protocols, keyId and nonce before authentication.
- **[minor]** Link uniqueness across paths is undefined (4.3, 4.4). The 'duplicate' reason exists, but nothing says whether an own launch can hold an env-token link and a discovery-bound instance link at once, or whether two discovery connections from one ProcessKey can both be welcomed. A hostile mod in the same JVM can race the real mod for whichever link wins, and grants and topics become ambiguous.
  - Fix: State that there is at most one live link per game_id (ProcessKey or instance launch) across env v1, env v2 and discovery, and that a second connection gets reject{duplicate}. Add the test to R2 and R3.

## Review: feasibility (Urteil: fixable)

- **[blocker]** Sections 0, 1.1, 11: three independent projects are bundled into one release gate. They are (a) multi-version and multi-loader builds, (b) foreign-launcher attach with pairing and account proof, and (c) full in-game parity with scopes, audit, undo and rate limits. Nothing ships until O1 (Wave 6, the 8th serial stage), which needs every one of ~30 packages plus 14+ owner-tested jars and the launcher matrix of 10.5. Today's mod is only ~1170 lines (one 227-line screen), and MOD_PROJECT_ID in mod-release.yml is still empty, so no jar has ever been published. The plan also ships all of it as one 'Mod 2.0'.
  - Fix: Cut three releases. R-A (0.2.0): the existing v1 feature set (friends list, invites, share/kick/stop, toasts) on 3 tracer nodes (26.3-fabric, 1.21.1-neoforge, 1.20.1-forge), own launches only. For own launches this needs only the loader widening in launch_env, M1, U1-lite and B3. R-B: foreign attach (RB, R1a, R1b, R2, R3, R4d, J1, J2, plus a minimal pairing dialog) still carrying the v1 message set. R-C: parity, shipped incrementally. Every release must be shippable on its own.
- **[blocker]** Sections 3.6, 8.3 and Appendix C contradict the node ranges in section 2. Appendix C itself lists in-range breaks. The 1.21.9-1.21.11 node covers `Identifier` and `init(int,int)` changes at 1.21.11, and the KeyMapping.Category introduced at 1.21.9 takes ResourceLocation before 1.21.11 and Identifier after it. The 1.21.2-1.21.8 node has the 1.21.6 render rewrite and a toast API change, and Minecraft.disconnect/PauseScreen.onDisconnect most likely changed inside 1.21.x as well (8.3 collapses 1.20.5-1.21.x into one row). Appendix C has no rows at all for Keys, Clipboard, Session (Minecraft.getMinecraftSessionService vs services(), authlib) or Lan, so the research is incomplete. The count of 14 jars is therefore an optimistic floor. Expect 16-18, each with its own owner test and metadata.
  - Fix: Plan one node per probable breakpoint from the start: 1.21.9-1.21.10, 1.21.11, 1.21.2-1.21.4, 1.21.5-1.21.8 (verify the real break points with the fingerprint tool before D0). Complete Appendix C (Keys/KeyMapping.Category, Clipboard, Session, Lan, disconnect, Toast per era) as a spike before M1 commits to a node list. Budget 18 jars in 3.6, 10.5 and 11.
- **[blocker]** Section 3.6 and package B2: the fingerprint check is under-specified and cannot do what is claimed ('claimable without launching the game'). (1) A remapped Fabric or SRG release jar carries intermediary or SRG names, so `javap` on the release jar cannot be matched against Mojang mappings. It must run on the dev (named) classes. (2) It only sees members referenced by our code. It does not see overridden methods (Screen.render/keyPressed/mouseScrolled/updateWidgetNarration, AbstractWidget.renderWidget). A changed override signature compiles against one version and is silently never called on another, which gives a blank or unclickable UI. (3) invokevirtual owners are resolved through the class hierarchy, but mapping files list declared members only, so it needs a mini linker. (4) It needs client jars and mappings for ~40 versions. One agent will not get this right in a single pass, and it gives false confidence.
  - Fix: Make B2 'verify every node by compiling against both ends (and one middle version) of its range' (a cheap Gradle matrix of compile-only checks). Add a descriptor-exact override check that works from superclass abstract/overridable methods. Keep javap fingerprinting only as a supplement, and run it on named classes with a hierarchy walk. Treat the owner smoke test of the oldest and newest version of each range as the real gate. Move B2 up to Wave 1 so V packages use it.
- **[blocker]** Sections 3.4, 11.1, U1/U2a/U2b/V*: the compat contract is designed against one era (26.3, the newest API with GuiGraphicsExtractor) and frozen before any second era exists. U1 builds ~11 compat classes, CompatScreen/Painter and the kit on 26.3 only. U2a and U2b then write ~15 UI classes on that contract. V1, V2a, V2b and V3 each own `compat/**` and `platform/**` entirely, and no package may touch them concurrently. When the first back-port (1.21.x) or 1.20.1 forces a signature change in CompatScreen, ScrollPane focus handling, EditBox construction or resize/rebuild state preservation, the fix needs edits in `ui/` and `client/`, which nobody owns after U2a/U2b merge. U2a/U2b also run in parallel with V1/V2a, which own compat/**, so any new compat method they need collides with them.
  - Fix: U1 must ship two eras before any UI package starts: 26.3-fabric plus the oldest 2.0 target, 1.20.1 (Forge or Fabric, GuiGraphics), with a throwaway screen exercising button, EditBox, scroll pane, narration and resize. Put `compat/` ownership by class and let U2a/U2b add compat methods with branches for all existing nodes, via an explicit orchestrator-merged 'compat additions' rule. Give V packages explicit rights to touch `ui/kit` for era fixes.
- **[major]** Section 2 and the wave order in 11.3 invert audience and risk. The 2.0 cut reasoning (19-25k projects on 1.21.1/1.20.1) is right, but those nodes (V2b 1.21.1, V3 1.20.1 Forge/Fabric) land in Waves 4-5, after four serial packages on 26.x. The 26.x nodes are the smallest audience and the least stable (NeoForge 26.3 is beta, and 26.2/26.3 signatures changed again). V1 also introduces NeoForge for the first time on the bleeding edge, and M1 proves the multi-version/multi-loader topology with a single node (26.3-fabric). The riskiest unknowns (Stonecutter multi-loader/branch topology, MDG moj-mapped NeoForge, MDG legacyforge 1.20.1, loom-back-compat remap) are therefore discovered in Waves 2-5.
  - Fix: Make M1 a topology spike with three nodes on three loaders (e.g. 26.3-fabric, 1.21.1-neoforge, 1.20.1-forge) producing a Hello-World jar that loads in each loader. Verify how Stonecutter handles node names like '1.21.1-neoforge'. Semver predicates (`>=1.21.2`) break if the node id is parsed as a prerelease, so node id and Minecraft version need separate fields or a branch-per-loader layout. Then do the popular eras first (1.21.1, 1.20.1) and the 26.x eras last.
- **[major]** Section 3.7 and B3: mod-release.yml's `build` job is specified as 'no secret, no cache' and builds all nodes, which means 14-18 cold builds in ONE job. Pre-26 Fabric nodes remap, and NeoForge/legacyforge nodes run NeoForm/Forge patch+decompile+recompile, which takes several minutes and ~0.5-2 GB each. The current workflow has `timeout-minutes: 30` and one job. Serial cold builds will exceed it by a wide margin. Section 3.6's CI matrix also risks the GitHub Actions 10 GB per-repo cache cap (14 nodes at 0.5-1 GB plus the three-OS Rust caches), causing constant eviction and slow runs.
  - Fix: Release `build` becomes a matrix (one job per node, no secret, no cache, artifact upload), followed by a `collect` job (still no secret) that writes jars.json and the sha256 list, followed by `publish`. In mod.yml cache only the Gradle wrapper and dependency caches, key per toolchain family (fabric-remap / neoforge / legacyforge) rather than per node, and use path filters so Rust-only PRs skip the node matrix. Add `fail-fast:false` and a nightly full run in place of a full run on every PR.
- **[major]** Section 11.2 U2a/U2b (and section 7): the in-game UI is mostly not agent-verifiable. Acceptance is 'builds on 26.3-fabric', 'no vanilla call outside the allowed set', and owner-verified layout, overlap and navigation at 320x240..960x540 (10.5) at the very end, after Wave 6. The UI is substantial: hub, 5 tabs, add-friend with 3 sub-tabs, scrolling rows with focus/narration, Ctrl+Tab/Ctrl+1..5 shortcuts, confirm flows, a wait screen and blocked/options screens. Nothing exercises it in CI, so layout, scroll and focus bugs surface only at the release gate. Vanilla Screen.init() also re-runs on every resize and wipes EditBox text and focus. Section 7.5 does not mention state preservation in `rebuild()`.
  - Fix: Split each screen into pure view-model + layout (Minecraft-free, in `core` or a `ui-model` source set on JDK 17: rectangles, scroll offsets, row heights, tab wrapping, text clipping through an injected `IntUnaryOperator` width function) and thin widget glue. Unit-test layout at the five resolutions with golden rectangle lists and a recording fake `Painter`. Add an explicit `rebuild()` state-preservation requirement and test it. Keep owner checks for rendering only.
- **[major]** Sections 5, 6, 7, 9 and 11.2 R4a/R4b: parity and consent are over-built for a first real release. They come to 27 ops, 8 topics with aliases and revision counters, 3 scopes plus danger, 20+ rate-limit rules, an audit ring plus a 7-day file, undo for 9 action types (needing a new `friends::block_peer`), six new commands/events, the AddedInGame review flow, a prompt queue, pairing sticky-deny/exe-path heuristics and a mock scenario. Most of this is only needed for add-friend/code/block/rename/danger in-game, which the launcher already offers. The 'Fertig'/danger/options/blocked screens are low-value in a game UI.
  - Fix: For parity v1 only do: accept/decline requests, add by name, invites (view/decline/join-here), share/kick/stop. Everything else uses `launcher.open`. Keep consent to the pairing prompt plus one scope prompt ('friends' and 'share', 'Nur diesmal'/'Für dieses Spiel'), a hard 5/10 min limit and a minimal audit list (in-memory plus launcher toast). Defer undo, the persisted audit file, danger ops in-game, code create/list/revoke, blocked list, rename and the Options tab to a later release. Drop the `friends`-scope 'settings.update' op entirely until needed.
- **[major]** Sections 5.1-5.7 and 11.2 R2/R4a: the full protocol v2 (correlation ids, whole-topic pushes with rev, 250 ms coalescing, drop-oldest event queue, in-flight caps) is coupled to the foreign-launcher goal even though foreign attach only needs the `attach` handshake, the account proof and the report. The existing v1 snapshot/notify/action message set already covers friends, invites and sharing. The spec itself builds a V1Adapter to translate v1 into topics, so the topic machinery is being built twice.
